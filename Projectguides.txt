## 1. Purpose

This guide explains how to install, run, test, extend, and deploy the repository baseline. The implementation is designed for transparent, user-controlled blockchain interactions.

The platform must always:

- show a human-readable transaction preview before authorization;
- require an explicit user action for every authorization request;
- keep transaction recipients, values, network, and calldata visible;
- avoid private-key handling in browser code and application services;
- support local and test networks before production deployment;
- preserve an auditable workflow record for every operation.

The baseline does not implement unattended authorization, hidden transaction replacement, custody, or automatic asset movement.

## 3. Prerequisites

Install the following locally:

- Node.js 22 or later;
- pnpm 10 or later;
- Git;
- a local PostgreSQL-compatible database for persistence work;
- Foundry only when working on Solidity contracts;
- a local blockchain simulator or public test network for integration testing.

Check versions:

```bash
node --version
pnpm --version
git --version
forge --version
```

Do not use production credentials in local development.

```bash
git clone https://github.com/lackx741-tech/Implementation.git

```

If the project tree has not been generated in a new checkout:


## 7. Frontend Implementation

### 7.1 Application Flow

The browser application follows this sequence:

```text
Boot
  -> Create session
  -> Discover provider adapters
  -> Connect selected provider
  -> Start workflow
  -> Render transaction preview
  -> Wait for explicit user confirmation
  -> Request provider authorization
  -> Submit returned signed object
  -> Show processing status
  -> Show final result
```

### 7.2 Inline Script Policy

Inline JavaScript is limited to application bootstrapping. Business logic must remain in versioned modules under `apps/web-dapp/src/`.

Good:

```html
<script type="module">
  import { startDemo } from './src/pages/WorkflowPage.js';
  const root = document.querySelector('#transaction-preview');
  if (root) startDemo(root, 'http://localhost:3000', '0x0000000000000000000000000000000000000000');
</script>
```

Do not place wallet selection, transaction construction, authorization loops, credentials, or hidden redirects in inline script blocks.

### 7.3 Modal Requirements

The transaction modal must display:

- application name;
- selected network;
- wallet address or account context;
- recipient address;
- native value and token amounts;
- decoded method name where available;
- contract address;
- calldata summary;
- estimated fee or resource information;
- a clear confirm button;
- a clear cancel button;
- a link to inspect the raw request.

The confirm button must be the only action that begins wallet authorization. A modal must not auto-submit, auto-connect, or auto-authorize on page load.

### 7.4 Provider Adapter Contract

Each provider adapter implements the shared interface in `packages/wallet-adapters/src/index.ts`:

```ts
interface WalletAdapter {
  readonly id: string;
  readonly displayName: string;
  isAvailable(): Promise<boolean>;
  connect(): Promise<WalletConnection>;
  disconnect(): Promise<void>;
  getAddress(): Promise<string>;
  getNetwork(): Promise<string>;
  authorizeTransaction(request: TransactionRequest): Promise<SignedTransaction>;
}
```

Adapters must:

- return the provider-reported account;
- return the provider-reported network;
- reject if the requested network is not selected;
- expose provider errors without suppressing them;
- never retain signing material;
- never change a request after the preview is displayed.

## 8. Builder Implementation

### 8.1 Builder Responsibility

A builder converts a selected, versioned workflow template into unsigned, reviewable transaction requests.

The builder must not:

- access private keys;
- sign transactions;
- hide transaction recipients;
- substitute recipients after preview;
- add an unannounced transaction;
- invoke arbitrary contract methods without a declared template;
- bypass the confirmation interface.

### 8.2 Builder Input

```ts
interface BuilderContext {
  chainId: string;
  recipient: string;
  account?: string;
  templateId: string;
  templateVersion: string;
}
```

### 8.3 Builder Output

```ts
interface BuiltRequest {
  transactionId: string;
  chainId: string;
  to: string;
  value: string;
  data: string;
  description: string;
  decoded?: {
    method?: string;
    parameters?: Record<string, unknown>;
  };
}
```

### 8.4 Builder Tests

Every builder requires fixtures covering:

- valid input;
- invalid network;
- invalid recipient;
- zero-value interaction;
- non-zero value interaction;
- decoded calldata;
- multiple requests and ordering;
- expiration;
- template version mismatch.

## 9. API Implementation

### 9.1 Current Routes

```text
GET  /health
POST /api/v1/sessions
GET  /api/v1/sessions/:sessionId
POST /api/v1/workflows
POST /api/v1/transactions/signed
```

### 9.2 Session Creation

Request:

```http
POST /api/v1/sessions
content-type: application/json
```

Response:

```json
{
  "session": {
    "id": "session-id",
    "status": "CREATED",
    "createdAt": "2026-09-26T18:24:08.000Z"
  }
}
```

### 9.3 Workflow Creation

Request:

```json
{
  "sessionId": "session-id",
  "chainId": "local-development",
  "recipient": "0x0000000000000000000000000000000000000000"
}
```

The response must include a workflow ID and preview records. The frontend renders these records before requesting authorization.

### 9.4 Signed Submission

The endpoint currently returns a queue acknowledgement. A production implementation must:

1. validate the workflow ID;
2. validate the transaction ID;
3. ensure the signed object corresponds to the displayed request;
4. reject expired or duplicated submissions;
5. append a status event;
6. enqueue a chain submission job;
7. expose a status reference to the client.

## 10. Event Model

All event records use a common envelope:

```json
{
  "eventId": "event-id",
  "sequence": 1,
  "occurredAt": "2026-09-26T18:24:08Z",
  "payload": {
    "type": "workflow_preview_ready",
    "workflowId": "workflow-id"
  }
}
```

Recommended event order:

```text
session_created
wallet_discovered
wallet_connected
workflow_started
workflow_preview_ready
authorization_requested
signed_payload_received
transaction_queued
transaction_submitted
transaction_confirmed
workflow_completed
```

Events should be append-only. Reporting tables may be rebuilt from events when projections change.

## 11. Smart Contract Development

### 11.1 Current Contract

`contracts/src/WorkflowRegistry.sol` is a non-custodial metadata registry. It stores template metadata and emits events. It does not hold or transfer assets.

### 11.2 Local Contract Commands

```bash
cd contracts
forge build
forge test
```

Run formatting:

```bash
forge fmt
```

### 11.3 Deployment Process

Use a local node or public test network first:

```bash
export RPC_URL=http://127.0.0.1:8545
export DEPLOYER_PRIVATE_KEY=<local-test-key>
./scripts/deploy.sh
```

The deployment key must be a disposable local/test key. Never use a production key in a repository shell, CI log, issue, or chat message.

### 11.4 Contract Acceptance Gates

Before any production deployment:

- compile with the pinned Solidity version;
- run unit tests;
- run static analysis;
- inspect generated ABI;
- verify deployed bytecode;
- test ownership transitions;
- test unknown-template handling;
- test event contents;
- perform independent review;
- document the deployed address and network.

## 13. Worker Implementation

Workers should consume typed jobs and produce typed results.

### Transaction Worker

- receives a validated submission job;
- loads the transaction record;
- calls the configured chain adapter;
- writes a submission reference;
- publishes a status event;
- retries only recoverable errors.

### Confirmation Worker

- polls pending submission references;
- detects confirmation, replacement, timeout, and failure;
- writes status history;
- publishes workflow updates.

### Projection Worker

- consumes workflow events;
- updates reporting tables;
- tracks projection checkpoints;
- supports replay from a selected event sequence.

### Export Worker

- validates the export request;
- executes a bounded query;
- writes an export artifact;
- updates export status;
- expires old artifacts according to policy.

## 14. Control Plane Implementation

The control plane should provide:

- workflow list with filters;
- transaction status list;
- configuration version history;
- template editor with preview;
- operator activity history;
- report dashboards;
- export job status.

Configuration changes must be versioned. A template change must not silently alter a workflow already in progress. Existing workflows retain the configuration snapshot used when they were created.


Create a session:

```bash
curl -X POST http://localhost:3000/api/v1/sessions
```

```bash
curl -X POST http://localhost:3000/api/v1/workflows \
  -H 'content-type: application/json' \
  -d '{
    "sessionId": "REPLACE_SESSION_ID",
    "chainId": "local-development",
    "recipient": "0x0000000000000000000000000000000000000000"
  }'
```

The returned workflow should be rendered in the frontend modal. At this stage, the baseline is a preview environment and does not connect to a live submission adapter.

## 19. Change Management

For every significant change:

1. Update the relevant interface or architecture document.
2. Add or update tests.
3. Add an architecture decision record if the design changes.
4. Update migration files for data changes.
5. Update this guide when developer workflow changes.
6. Record the change in the repository changelog.

Do not combine unrelated architecture, data, and deployment changes in one unreviewed commit.

---

## 20. Definition of Done

A feature is complete when:

- its contract is documented;
- its implementation is typed;
- its tests pass;
- its state transitions are observable;
- its errors are handled;
- its user-visible behavior is clear;
- its operational behavior is documented;
- its deployment impact is understood;
- its rollback or recovery path is known.
